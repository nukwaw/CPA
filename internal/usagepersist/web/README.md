# Embedded statistics and quota adapter

This package, under `internal/usagepersist/web`, contains the dependency-free statistics page and the adapter for the upstream management quota page. It has no npm dependencies, network fonts, CDN scripts, or generated frontend bundle. The page is served at `/stats.html`; its assets use the single canonical `/stats-assets/*` namespace exported as `AssetsPrefix`. The adapter uses `window.CPAQuotaPersistence`, the `cpa-quota-persistence-status` event, the `data-cpa-quota-persistence` marker, and the `X-CPA-Quota-Persistence` response header. A separate, deliberately small navigation asset (`management-nav.js`, marker `data-cpa-stats-nav`, `window.CPAStatsNav`) adds the sidebar entry that opens the page. There are no prototype namespace aliases.

## Server integration

- Serve `Asset("stats.html")` at `/stats.html` and the five JavaScript/CSS assets at `/stats-assets/:name`, retaining the returned MIME type and sending `X-Content-Type-Options: nosniff`.
- Management APIs remain behind the existing management authentication middleware at `/v0/management/stats`. Static assets contain no credentials.
- Call `InjectManagementHTML` on the in-memory management HTML response, not the updater's file on disk. If it returns `false`, serve the original unchanged page and emit a compatibility warning. It does not replace the management application or alter quota-card markup/styles.
- The injector loads the bridge and the navigation asset before the original inline module, wraps the verified native quota helpers and selected source initializer expressions, then appends an explicit store adapter inside that same module's lexical scope. It verifies the complete generated quota store/setter/clear/capture/commit sequence, filename splitter, source resolvers, provider configs, and final registry relationships; only lexical identifiers may vary. Unknown, duplicate, or partial selector coverage leaves the original document unchanged. Source wrappers observe inputs or actual results and return the original value/Promise unchanged; they never rewrite requests, add provider calls, guess global stores, or inspect React internals.
- Only an enabled `GET /management.html` receives document adaptation. Source-file conditional cache validators are removed from a cloned local request so a pre-upgrade cached page cannot indefinitely revalidate without the adapter. The exact original request is restored afterward; its headers and body are not mutated. Successful augmentation emits `Cache-Control: no-store`, removes source validators/checksums and range advertisement, and repairs the content length. Partial, encoded, overflowing, flushed, unsupported, and error responses retain their original bytes. Inference requests, streaming, and WebSocket routes are not intercepted.

The store initializer patterns, cache schemas, window identities, and auth lifecycle were inspected in the actual `router-for-me/Cli-Proxy-API-Management-Center` source at commit `4530da271ba2e89810d4dccebc57f3091afa590a`. Injection was tested against a real Vite single-file build of that checkout, not only a hand-written fixture. A later incompatible minifier or upstream store change deliberately disables the adapter instead of breaking the original UI.

## Authentication and safety

The statistics page sends a management key in `Authorization: Bearer ...` only to its same-origin API. By default the key stays in memory. The optional checkbox saves it to `sessionStorage` for that browser tab; disconnect clears it. The dashboard does not read/decode the management application's saved password and never puts secrets in URLs. Existing server cookies, if supported by the host, use same-origin credentials.

The navigation asset never reads the management key. On a plain left click it asks the attached bridge (`armStatistics`) to write the same tab-scoped `sessionStorage` entry the dashboard's own "remember for this tab" checkbox uses, then navigates; the key value never enters markup, the status object, or a return value. Modified clicks (middle, new tab/window, or with a modifier key) keep their native behavior and load the dashboard without a handoff. The entry is added to the verified `aside.sidebar .nav-section` markup, is re-added idempotently after a sidebar re-render, leaves the page unchanged when that markup is absent, and is the only DOM node this add-on adds.

The bridge obtains the active management connection only from the explicitly attached auth store. Cross-origin management connections are not bridged: their keys must not be forwarded to the server hosting this page. The bridge itself does not persist keys, expose them in its status object, or copy auth-file response objects into its caches.

All model/provider/error text is rendered with DOM text APIs, never raw HTML. CSV cells protect against spreadsheet formula execution. Quota observations are recursively allowlisted for each of the seven verified provider state shapes; tokens, response bodies, error strings, and xAI user/team IDs are dropped. Cache batches are bounded below the backend's request-body limit. The recorded quota window history stores only the window id, its used percentage, the observation source, and the observation time for a credential generation; the side window renders it as an SVG built from DOM nodes, and its value estimate is labelled as a local estimate rather than a provider invoice.

## Statistics behavior

Persistence passively consumes the original built-in CPA usage provider's already-gated payload; it is not a separately enabled collection feature. The existing `usage-statistics-enabled` setting (v8: `observability.usage.usage-statistics-enabled`) retains its original behavior and reload controls. No shared-SDK gate, record format, publication, or drain behavior is changed. `USAGE_PG_DSN` selects an independently owned usage-only PostgreSQL pool, with optional `USAGE_PG_SCHEMA`. Without it, standalone runs use an instance-local journal under the existing `WRITABLE_PATH`/auth directory conventions. CPA configuration/authentication storage is not changed, and there is no additional collection toggle.

Storage initializes independently of inference startup. Usage and original management observations enter a bounded asynchronous queue of 256 sanitized records plus at most one in flight; optional storage I/O does not block those callbacks. Overflow, write errors, and shutdown cancellation can lose observations, and there is no durable retry spool. The native journal supports at most 64 MiB and 100,000 unique events, without pruning retained history. These are supported storage limits, not exact process-RSS guarantees; decoding and concurrent queries need headroom.

The dashboard reads `collection_enabled` from `/v0/management/stats/status`. When it is explicitly `false`, an informational notice explains how to resume built-in collection. Previously stored history, pricing, and quota remain available while storage is healthy, and the notice does not disable filters, refresh, exports, or pricing actions. Storage-write failures and bounded-ingestion `dropped_events` are shown together with the collection notice; drop warnings include queue-overflow and validation-failure counts. Pending admissions are informational and may include the one in-flight event in addition to the bounded queue. There is no new collection toggle. Missing health fields from an older status response do not imply disabled collection or data loss. An unavailable storage response (`available: false` or HTTP 503) explicitly warns that persistence is unavailable while the original management page and manual quota refresh remain available.

The page has four tabs: **Overview** (merged totals line, traffic chart, composition, and the model/provider performance tables), **Requests** (the live request stream), **Quota** (one saved-state card per attributable credential plus a per-credential side window), and **Pricing & sync**. Overview, Requests, and Pricing share explicit date/model/provider/result filters; there is no header statistics strip and there is no credential or API key ID filter or column, because per-credential traffic is reached through the quota side window. All-history queries supply an explicit epoch lower bound instead of relying on the backend's last-24-hours default. Charts use timestamp spacing and label downsampled series; newest data is retained. Requests shows newest-first, paginated completed executions. Polling pauses for hidden/offline pages, older request pages, a paused stream, and a paused side window, and backs off on errors. A failed update preserves the prior snapshot with a visible warning rather than replacing it with misleading zeros.

Each request entry carries its own detail instead of a credential column: the requested model and provider, the reported response model (flagged on the entry and its row when it differs from the requested one), the requested and reported service tier (flagged when they differ), total tokens, throughput, cache read share, latency, first-token time, and cost. Throughput is complete output tokens over total request time and cache read share is cache reads over input tokens, both matching the keeper dashboard and both shown as unknown rather than zero when the base is absent. A failed execution exposes its sanitized bounded provider message as a hover/focus detail on the result badge; the dashboard never renders the stored text as markup.

The Quota tab reads `/quota`, `/quota/identities`, and `/quota/cache` together and reduces every provider's saved state shape — Claude windows, Kimi rows with untranslated keys and used/limit counters, grouped buckets, billing objects, or a normalized snapshot fallback — to the same labelled percentage line. An absent value stays absent instead of rendering as zero, and a credential without saved windows explains how to populate them. Selecting a card opens a modal side window for that credential: its recorded window history, the estimated value of the requests attributed to it, and a request stream scoped to that credential. The window selector defaults to automatic, which charts the window the server reports as most observed; the explicit choices come from the normalized provider snapshot first, because recorded window ids are normalized ids and display-state ids can differ. A 7/14/30-day range drives both the history and the value estimate, and the stream refreshes every five seconds while open and is pausable. The identities key is displayed as its file name; the internal NUL-separated suffix is never rendered.

Prices are USD per million tokens, not provider invoices. The fixed Models.dev sync source preserves manual overrides. Unknown prices remain unpriced; missing catalog cache rates are not displayed as free. The catalog can contain thousands of rows, so rendering is limited to the first 200 search matches with an explicit notice. Search still covers every downloaded model rate. Storage-health warnings identify potential gaps after persistence failures.

## Quota fidelity

A file-backed credential is published only while its backing file still describes the same credential the runtime observes, so an out-of-band rewrite or deletion withdraws its identity instead of leaving stale state visible. The comparison restates the file's metadata and keeps runtime attributes, because core derives some identity-bearing attributes for file credentials (Kimi's `domain`/`base_url`, for example) that a file cannot restate; without them every Kimi credential would be unverifiable and could never persist its quota display.

Authenticated `GET /v0/management/stats/quota/identities` supplies `{bindings:[{provider,key,account,account_kind,auth_index,manual_source_proof?}]}`. The key is the original frontend key (Devin uses filename + NUL + auth index). A binding carries account **facts**, not an opaque credential identity: `account` is the label the credential publishes (empty when it publishes none) and `account_kind` is `email`, `device_id`, or empty. A card is therefore keyed by `(provider, key)`: **one card per credential file**, which is the unit the control panel's own quota page uses (its identity is the auth-file name, with a filename+NUL+auth-index exception for Devin). Two credentials that publish one account stay two cards, because they are two credentials that can each be refreshed, and a credential that publishes no account keeps its own card instead of being merged with an unrelated credential that also publishes none. The account stays a recorded fact on each card: it is titled by its credential file, with the account, provider and last observation shown as detail. The account fact still scopes the side window, so `(provider, account)` remains usable for filtering and grouping without keying the cards. Durable state stays keyed by `(provider, account)`, so a credential file can be renamed without orphaning its saved history. `auth_index` is the transient request-start correlation value only: it is never persisted, never used as a map key, and never uploaded. The optional proof is `{v:1,selector_hashes:{account_id?:sha256,project_id?:sha256,user_id?:sha256}}`, using lowercase SHA-256 hex over the exact UTF-8 selector value recognized by the server. Missing, malformed, unsupported-version, or unrecognized-field proof is unknown, never a wildcard. Proof hashes are retained only in a private WeakMap keyed by the allowlisted binding object. The bridge does not derive credential/email fingerprints, independently download auth files, retain raw selectors, or expose proof in state/status. Successful rendered states still upload **only** `{provider,key,account,account_kind,observed_at,state}` through `/quota/cache`; neither proof nor selector hashes are included. The binding is captured at native operation start, never at success or retry.

The identity GET also primes the server's immutable advisory publication. Original management handlers read that publication without touching the live credential manager; the independent writer revalidates captured proof authoritatively. A manager read lock can cover core storage I/O, so no live lookup is allowed on the shared usage callback or original-handler chain. An original management request arriving before an explicit full add-on identity/read may skip optional observation; it is never delayed waiting for proof. There is no background refresher. The bridge's ordinary identity-first flow primes proof before its operations.

`wrapCapture` saves an immutable binding-map sidecar keyed by the original native generation object in a WeakMap and returns that object unchanged. `wrapCommit` changes only the callback argument; the original guard, default arguments, return value, and exceptions remain authoritative. During its synchronous callback, subscriptions can associate success with the captured binding. The seven-provider batch loader is different: it commits each result *inside* an outer store updater, so its subscription runs after the commit callbacks. A verified `wrapUpdater` around the original `resolveUpdater` carries those callback scopes to that exact returned map in a WeakMap. Unchanged entries, ambiguous scopes, unknown-at-start operations, and unguarded store writes never become new persisted observations. No sidecar fields are added to quota UI state.

Native capture timing alone does **not** prove a retained auth-file item's selector. If a same-file/index credential changes A → B, an old item can still send account A while native capture sees binding B; a token valid for both accounts can make that request succeed. The bridge therefore also snapshots a private opaque filename source-fence token (and a global fallback token) in each capture. Exact source-index or selector mismatch/unknown proof rotates the relevant token to a brand-new object. Both success queueing and PUT flush/retry require the originally captured token to remain current. A later matching fetch or ordinary identity poll cannot re-stamp/revive an old capture. These negative fences never call native clear, rewrite UI state, block the original request, or disable manual refresh. Session resets may reset source fences; ordinary refresh does not. Batch mismatches affect only the relevant filename, and ambiguous overlaps conservatively drop optional persistence.

Confirmed source coverage at the pinned commit:

- **Codex:** wraps the lexical fetch initializer before provider-config and registry initialization, not merely a config/adapter property. The injector verifies its snake-first `normalizeAuthIndex(file.auth_index ?? file.authIndex)`, exact account resolver and header-builder relationship, plus the reset's `await consume; lexicalFetch(file, t)` relationship. The projector evaluates the actual compiled account resolver once; it does not equate generic `account_id` with the real direct/chatgpt-account/id-token resolution. Thus auth cards, page refreshes, batches, and post-consume reset fetches all observe the actual retained item. Digest checking is bounded, dependency-free, synchronous SHA-256 and works on insecure HTTP origins.
- **Antigravity:** wraps the actual asynchronous project resolver and observes its one original Promise result, including metadata/attributes and downloaded top-level/installed/web paths. It never calls that resolver twice or infers from entry-only aliases. A per-file pending gate exists before calling the original resolver and blocks optional queue/PUT while unresolved; the original Promise and provider network path remain unchanged. Concurrent unresolved resolutions conservatively fence their captures.
- **xAI:** observes the actual unpaid header builder's returned `x-userid`, produced by the real compiled user resolver, and matches it against the server-recognized `user_id` digest. The paid fixed-token path retains exact snake-first index validation without demanding a user selector it does not send. An unpaid unknown/mismatched selector that later falls back to paid health remains conservatively fenced; no late restamping occurs.
- **Claude/Kimi:** verified fixed-token requests retain their existing semantics with exact snake-first index validation. **Devin:** its actual shared fetch initializer retains camel-first index validation and filename + NUL + index cache keys, including in-flight sharing/native generation behavior.
- **Meta is not selector-proof closed by this contract.** Its quota request uses a literal DCA bearer read from downloaded file content, not merely server-selected `$TOKEN$`; the proof schema contains no evidence for that downloaded DCA value. Its existing native generation/binding provenance and display caching remain unchanged, but must not be described as universal source-selector proof. No Meta credential/token hash is invented by the browser. Closing this path needs a separately verified server/backend contract and actual download-to-request observation.

All seven provider adapters share `useQuotaActions`, `AuthFileQuotaSection`, and `useQuotaBatchLoader`; both Codex reset actions capture before reset/fetch. Devin auto-load delegates to the batch loader. Meta's inner `captureCurrent` helper is an empty native-guard check, not a successful observation; it does not replace the outer request-start binding. Original function bodies, request arguments, inference calls, success/loading/error shapes, labels, card bodies, notification callbacks, and actions are unchanged. Wrappers preserve `this`, arguments/default arguments, thrown identity, return identity, and Promise identity.

Hydration fills only absent/idle entries whose stored account facts still match the current binding for that provider and account. A restarted runtime may republish the same account with a different token; the account facts keep permitting historical cache hydration, which is never uploaded as a new success. Cache and normalized payloads are bracketed by identity fetches and checked again before applying. Latest-issued refresh fencing prevents reverse-order identity/cache responses from restoring an older binding. The original observation timestamp is retained privately; the original quota page is intentionally not given a new freshness badge.

The core producer stamps the account facts where the live credential is known, so a header sample is attributed by provider and account: account-labeled Codex and Claude credentials attribute their rate-limit headers, and a same-account token rotation keeps updating the same state. A credential that publishes no account property has empty account facts; it is grouped under its provider alone and is attributed there rather than dropped. No token is ever part of the attribution. Newer eligible normalized observations from `/quota`, including verified management observations, can overlay known windows without refreshing unrelated values. A mapped newer window without `reset_at` clears that window's old reset timestamp and label/hint instead of mixing fresh usage with an expired display-cache reset. The backend already retains valid future resets where appropriate; the adapter never invents a refill or reset time. Unrelated windows and stale incoming observations are left unchanged. Codex and Claude have verified normalized-to-display mappings, including Codex additional-limit windows matched uniquely by observed name and duration. Durationless Codex observations are not guessed as five-hour or weekly. Other providers' successful rendered caches hydrate, but normalized windows whose identities cannot be mapped unambiguously are ignored rather than assigned to the wrong card.

The adapter compares the timestamps available in existing payloads and persisted observations. These comparisons do not guarantee exact upstream header-arrival times, ordering between independent observation sources, or stronger SDK delivery/shutdown-drain behavior. Persistence leaves the original provider and shared SDK manager semantics unchanged.

Status is available through `window.CPAQuotaPersistence.status` and the `cpa-quota-persistence-status` event. These expose status/counts and original cache observation time, not credentials or bindings. Synchronization failures also warn in the console; manual upstream refresh continues working. Membership of the current binding table is the whole operation fence: an operation is persistable only while the binding it started under is still present. A removed or newly proven binding fences its filename with the original `clearQuotaCache([filenames])`; an unchanged poll fences pre-poll captures without clearing the settled display the management page already shows. An unchanged poll therefore keeps settled success/error/idle values with their observation and window freshness sidecars, while loading states and old pending uploads are not restored. An account replacement or deletion clears affected state and suppresses pre-replacement history within the tab, including A-to-B-to-A transitions. User-initiated file/global resets retain their original scopes.

A 409 is terminal for the returned batch: it is never re-stamped or retried. Native clearing applies only to a still-current binding and operation that has no newer valid pending work for that filename. A late A conflict therefore cannot clear replacement B's display or discard B's queued upload; mixed batches are scoped the same way. Non-409 retries retain their original binding and are discarded on replacement/reset/session change. A fresh identity lookup can authorize new operations, not revive old captures.

Core `Generation` also advances on ordinary execution results (an execution result, a cooldown change, an auth-file write, or a failed token refresh), so no per-operation version is stable during benign activity. A client upload is therefore decided by the account facts and the binding table rather than by any version: `/quota/cache` accepts an observation whose `provider`/`account` pair is still published, and only a genuine replacement is refused with 409. Without that rule a successful manual refresh could be discarded — and its displayed card cleared — because an unrelated auth-file write happened between the identity read and the upload. Both credentials of one account remain legally correlatable and share the single persisted row the backend keeps for that pair, so a same-account rotation neither fences the other credential nor loses the card.

## Tests

```sh
node --test internal/usagepersist/web/web_test.cjs internal/usagepersist/web/manual_source_test.cjs
go test ./internal/usagepersist/web
CPA_MANAGEMENT_FIXTURE=/path/to/upstream/dist/index.html go test ./internal/usagepersist/web
output="$(mktemp -t cpa-web-build)" && go build -o "$output" ./cmd/server && rm "$output"
```

The built-in-module [Node regressions](web_test.cjs) cover health/capacity notices, filters/charts/pricing, CSV and DOM safety, reset removal, immutable operation provenance, replacement/deletion/ABA, unknown-at-start refusal, unchanged-poll settled-state preservation, per-credential-file cards (two bindings of one `(provider, account)` stay two cards, an account-less credential never merges with another, and no removed credential identity is ever read), late-409/retry fencing, the statistics sidebar entry (idempotent mount, unknown markup, click semantics, no key access), and the tab-scoped handoff. Controlled promises and timers exercise reverse completion order without sleeps.

Go fixture tests verify exact recognized helper/source shapes and full injected-module syntax. [Compiled helper tests](compiled_helpers_test.cjs) execute all seven native setters, batch timing, native guards/defaults, identity/throws, and Devin key invalidation. [Compiled source tests](compiled_sources_test.cjs) exercise the verified Codex, Antigravity, and xAI selector paths, including stale inputs, overlaps, actual resolver results, private proof handling, and original return/Promise behavior. Seven-setter coverage is **not** universal seven-provider source-proof closure; the Meta limitation above remains.

The [lexical fixture](manual_sources_fixture.json) comes from the pinned checkout's TypeScript AST. [Templates](source_templates.go) vary only identifiers and enforce cross-node relationships. The optional [extractor](extract_manual_fixture.cjs) and [template generator](generate_source_templates.cjs) read a pinned checkout and write stdout; they need its installed TypeScript only for regeneration and never modify upstream files. `CPA_MANAGEMENT_FIXTURE` selects a real single-file build for the same checks. [Middleware tests](../management_middleware_test.go) additionally cover pre-upgrade 304 handling, restored request identity, inference-route isolation, ranges/preconditions, compressed bytes, overflow, and error fallbacks.

### Recorded acceptance scope — statistics entry and durable upload identity, September 29, 2026

A real single-file management build of the pinned checkout was served from a locally built `cmd/server` and driven by headless Chromium (CDP) against local mocked Claude and Kimi upstreams:

- The sidebar rendered one `Usage statistics` `a.nav-item` inside `.sidebar .nav-section`, and it survived a route change and a sidebar collapse/expand re-render.
- Clicking it navigated to `/stats.html`, handed over the tab-scoped key, and the dashboard reported `Connected` with no auth dialog and no failed requests.
- Both a Claude and a Kimi manual refresh whose captured request-start revision had been invalidated by a benign auth-file write (`R1 != R2`, identical credential generation) uploaded with **HTTP 200** and kept their card values; the previous build returned 409 and the cards reverted to `Click here to refresh quota`. Both fresh observations were read back from `/v0/management/stats/quota/cache`, and both cards were still filled after a route change, a full reload, and an eight-second wait.
- Before the reconciliation fix, a Kimi file credential produced **no** identity at all, so no Kimi quota state could ever persist; it now publishes normally while a genuinely different file credential is still refused.
- An OAuth token rotation for the **same account** kept the credential generation and the displayed card: before the account-scoped identity fix, Kimi's generation changed on every refresh, so the card reverted to `Click here to refresh quota` on the next page load. Handing the same file to a different account still withdrew the generation and hid the cached entry, and returning to the original account restored both.
